# Stop Making Pretty UIs. Think Like a Product Designer

## Summary

Kole Jain argues that learning only UI design (styling a landing page or a button) is like decorating a single room, while product design is designing the whole house: the flow, the function, the wiring and how it all connects. He builds product design on three ideas. First, design every state users actually meet (empty, loading, success and error), not just the happy path. Second, build for flow: think in screens and sequences instead of website sections, and ask how the user got to a screen and what they need next. Third, use a design system for clarity, keeping buttons, spacing, type and color consistent so people trust the product and every new screen feels familiar. For someone building a design system, this sets the purpose of the system (trust and speed through consistency, not decoration) and adds state coverage and flow thinking to the checklist for every component and screen.

## Key Ideas

- UI design is decorating one room; product design is designing the whole house, including flow, function and wiring.
- Polished visuals alone do not get people hired; a portfolio of products that solve a problem makes landing a job much more likely.
- Linear is loved for its clarity (states, flows and system), not only for how it looks.
- Most designers design only the happy path, but real apps must handle empty, loading, success and error states.
- A thoughtful empty state, like Dub's, has an animation, a message and a clear next step, so users are not left staring at a blank screen.
- Giving immediate status after an action (such as a build status after a deploy) keeps users informed and in control.
- Design an application in screens and sequences, not in sections the way you would a website.
- When building a flow, ask how the user got there and what they need next.
- A flow is a chain of tiny decisions, and product design is making those transitions feel natural.
- A design system is not just aesthetic; it is how users build trust and speed with the product.
- Consistent meaning builds trust: in a macOS pop-up the primary color is always the non-destructive action.
- Keeping button spacing, type scales and color scheme consistent makes new screens, such as a new modal, easy to build and familiar to use.
- A design system is not about having hundreds of components; it is about making decisions you can stick to.

### Decisions it informs

- What should a screen show when there is nothing in it yet? (`Q-pattern-04`)
  - A blank screen: The user is left staring at an empty screen with no idea what to do. When: The source never recommends it.
  - A thoughtful empty state: An animation, a message and a clear next step or call to action (Dub's dashboard; in the hiring tool, a prompt to start posting job links). When: Any list, dashboard or area that can be empty, such as no hires to manage.
  - Recommendation: Use a thoughtful empty state with an animation, a message and a clear next step, because it guides users instead of leaving them facing a blank screen.
- How should the product report the result of an action that takes time, like a deploy or connecting an integration? (`Q-state-08`)
  - No status: Users are left guessing whether it worked. When: The source never recommends it.
  - Loading state, then success or error: An informative loading state while it runs, then a success message or an error message (or an immediate build status notification, as in Vercel). When: Deploys, integrations and other actions whose outcome is not instant.
  - Recommendation: Show an informative loading state and then a clear success or error message, because it keeps users informed and in control.
- Should you structure the product like a website or like an application?
  - Sections, like a website: Each part is designed as a standalone section or page. When: The source associates this with websites.
  - Screens and sequences, like an application: Each screen is designed as a step, with attention to how the user arrived and what they need next. When: Real applications and product flows.
  - Recommendation: Think in screens and sequences for applications, asking how the user got there and what they need next.
- When a user finishes creating something, should the flow end or lead them onward?
  - Close everything on create: The task ends; the new item may be incomplete, like a team space with no members. When: The source mentions it only as what Notion could have done.
  - Prompt the next step, with a skip option: The user is led straight into the natural next task (add team members) but can skip it. When: When the created item is not much use without a follow-up step.
  - Recommendation: Prompt the natural next step with an option to skip; the source calls Notion's version a thoughtful user flow.
- What makes a design system worth having: many components, or a few decisions held consistently?
  - Hundreds of components: A large library; the source says this is not what the system is about. When: Not recommended by the source.
  - A few decisions you stick to: Button spacing, type scales and color scheme stay the same everywhere, so new screens feel familiar and users build trust and speed. When: Always, and more so as the product gets more complex.
  - Recommendation: Make decisions you can stick to and keep them consistent across every context, because clarity and trust come from consistency, not component count.
- In a confirmation pop-up, which action should carry the primary color? (`Q-state-06`)
  - The non-destructive action: The primary-colored button is always the safe choice, so users learn to trust it (the macOS convention the presenter says has saved him many times). When: Confirmation pop-ups that offer a destructive and a non-destructive action.
  - Whichever action the screen wants to push: The meaning of the primary color changes from dialog to dialog, so users cannot rely on it. When: The source never recommends it; it is the opposite of the consistency it praises [inferred].
  - Recommendation: Give the primary color to the non-destructive action and keep it that way everywhere, because users trust a convention that never changes.

### Process

1. Go past UI into product design: Move from styling single screens (a landing page, a button, a portfolio) to designing the flow, function and connections of a whole product that solves a problem.
2. Design the states: For each feature, design beyond the happy path: empty states with a message and next step, informative loading states, and success or error messages when an action finishes.
3. Build for flow: Think in screens and sequences; for each screen ask how the user got there and what they need next, and chain the tiny decisions so transitions feel natural (for example: click to contact an applicant, pick an email template, then choose whether to add other applicants before sending).
4. Systemize for clarity: Pull out components and keep button spacing, type scales and color scheme the same everywhere, so new screens such as a modal are quick to assemble and feel familiar.
5. Stick to the decisions: Hold to the decisions you made rather than growing hundreds of components; combined with strong flows and real states, this turns page design into product building.
