## Summary

The animations.dev home page is the sales page for Emil Kowalski's paid web animation course, so it mostly outlines what the course teaches rather than teaching it. Its core argument is that code alone does not make an animation work: a bad easing or duration can ruin an otherwise great animation, and a great animation comes from choosing the right ingredients, namely the easing, the duration and which properties to animate so it stays performant. The course structure doubles as a checklist for a design system's motion work: know why some animations feel better, how to choose easing and duration, when to use springs, when not to animate at all, and how to use AI; then implement with CSS first and Motion (formerly Framer Motion) second, and finally move from good to great through orchestration, conveying feeling, accessibility and performance. It also names Emil's credentials (Linear, Vercel's design system, and the Sonner and Vaul libraries) and lists the 15 AI skills bundled with the course.

## Key Ideas

- Code alone does not make an animation work; a bad easing or duration can ruin an otherwise great animation.
- A great animation is built from known ingredients: the right easing, the right duration, and the right properties to animate so it stays performant.
- Knowing the ingredients replaces guessing ('Does this easing work?', 'Is this enter transition too long?') with confident choices.
- Many tutorials, and Framer Motion's own documentation, follow a happy path and do not show how to build complex animations or what to do when something breaks.
- Animation theory covers easing, spring animations, timing, purpose and taste, including when you should not animate.
- Which easing and duration you chose, and why, is often more important than the code itself.
- Get CSS animations right first (transforms, transitions, keyframes) so moving to Motion is easy.
- Going from good to great involves conveying feelings through animation, orchestration, accessibility and performance.
- Build animations by first thinking and talking about the animation you want, then coding, improving and iterating.
- The Dynamic Island walkthrough uses spring animation to make the motion feel organic and natural.
- Animation theory applies beyond code: to prototypes, designs and anywhere else.
- Animations on the web can be treated as a form of art, with care for how they look, feel and behave, aiming for a moment of joy.

### Process

1. Decide whether to animate: Start by asking whether the element should animate at all and what the animation's purpose is (purpose and 'when you shouldn't animate' are theory topics). [inferred]
2. Choose the ingredients: Pick the easing, the duration, and which properties to animate so it stays performant; use a spring when the motion should feel organic. [inferred]
3. Think and talk first: Describe the animation you want before coding, then move to the code.
4. Code, improve, iterate: Implement (CSS first, Motion for complex cases), then refine and iterate, noting which easing and duration you chose and why.
5. Take it from good to great: Review the feeling it conveys, orchestration between elements, accessibility and performance. [inferred]
6. Use AI skills for review: Coding agents with the course's skills can review animations, suggest improvements, improve performance and answer motion questions.
