# Contributing to OpenDesigner

Thanks for helping. OpenDesigner is an open-source, AI-first way to create a design system: a set of skills, knowledge files and a small engine that any capable model (Claude, ChatGPT, Codex and others) uses to interview a person, recommend sourced defaults and write design tokens. Everything it recommends traces back to research in this repo, so there are two kinds of contribution: improving the product and improving the evidence.

You do not need to be a designer. Engineers, designers, accessibility specialists, writers and translators all have useful work here, and so do AI agents working on your behalf.

## Ways to contribute

| You want to | Start here | What a good contribution looks like |
|---|---|---|
| Fix a wrong fact, value or dead link in the research | [Research correction](.github/ISSUE_TEMPLATE/research-correction.yml) issue, then a PR to the lane file | The corrected value, a Tier A source (the system's own docs or spec), and the source logged in the lane's trace |
| Add a building block or a Decision Card | [New building block](.github/ISSUE_TEMPLATE/building-block.yml) issue | A card in the format in [`_coordination/SCHEMA.md`](_coordination/SCHEMA.md), with options, visual effect, what it depends on and affects, and sources |
| Improve the interview or a skill | [Skill or interview improvement](.github/ISSUE_TEMPLATE/skill-improvement.yml) issue | A transcript or screenshot of where the interview went wrong, and the change to the skill or questionnaire |
| Make OpenDesigner work in another AI tool | [Host support request](.github/ISSUE_TEMPLATE/host-support.yml) issue | The host's documented way to load skills, instructions or MCP servers, tested by hand, plus install steps for the README |
| Fix a bug in the engine or a skill | [Bug report](.github/ISSUE_TEMPLATE/bug-report.yml) issue | A failing command or test, then the fix with a test |
| Add a worked example | Open a building-block or skill issue first | A complete example folder with `DESIGN.md`, `decisions.md`, tokens and a preview, generated by the engine |
| Translate docs or the interview | Open an issue titled "Translation: <language>" | Translations of `README.md`, `docs/` or the interview copy, reviewed by a second native speaker |

Browse [good first issues](https://github.com/ckryptickunal/OpenDesigner/labels/good%20first%20issue) if you want something small and well scoped. Most of them are research gaps that each lane listed in its "Open questions / gaps" section.

## Ground rules

1. **Cite everything.** Every factual claim in `research/`, `benchmarks/` and `synthesis/` carries a source id such as `[S-L01-012]` that points to a row in `traces/<lane>-trace.md`, or it is marked `[inferred]`. Never present an inference as a fact.
2. **Use the source tiers.** Tier A is primary (a system's own docs, W3C specs, platform guidelines). Tier B is a recognized practitioner (NN/g, a design team's engineering blog). Tier C is community opinion and needs corroboration. The full rules are in [`_coordination/SCHEMA.md`](_coordination/SCHEMA.md).
3. **Disputes are settled by sources, not votes.** If two sources disagree, record both, say which one wins and why (newer, more primary, or measured). See [`GOVERNANCE.md`](GOVERNANCE.md).
4. **Reference intake never copies identity.** Examples and extraction may copy structure and quality from a reference, never another brand's logo, name, typeface files, illustrations or signature colors presented as your own.
5. **Plain language.** Write for an engineer who is new to design. Short sentences, real values, no marketing words.
6. **Never commit secrets.** `.env` and key files are git-ignored. Keep them that way. If you commit a key by mistake, revoke it first, then tell a maintainer through private reporting (see [`SECURITY.md`](SECURITY.md)).
7. **Skills ship offline.** Anything inside `skills/` uses the Python standard library only and makes no network calls.

## How the files fit together

```
research/<lane>.md        Decision Cards (### DC-Lxx-nn) with sources
traces/<lane>-trace.md    every source each lane opened, including rejected ones
benchmarks/               25 design systems torn down with real values
synthesis/                ontology, questionnaire, levers (dials and formulas), decision graph
skills/                   the product: Agent Skills that run the interview (source of truth)
data/                     knowledge chunks built from synthesis/ for the skills
examples/                 complete worked design systems
tools/                    od.py (coordination), jev_nav.py (research navigation and checks),
                          build_data.py, sync_skills.py, build_dist.py, check_links.py
_coordination/            brief, protocol, board, decision log, session heartbeats, inbox
```

`skills/` is the source of truth for the skills. The copies in `.agents/skills/` and `.claude/skills/` are generated by `tools/sync_skills.py`; edit `skills/`, then run the sync.

## The self-improvement loop

OpenDesigner is meant to get better every time someone uses it.

- **Using OpenDesigner in your own project?** When you or your AI agent hit a gap, a bug or a confusing step, run `python3 <skill>/scripts/engine.py feedback`. It prepares a pre-filled issue link for this repository. Nothing is posted automatically: you read it, edit it and submit it yourself.
- **Fixing it here?** Change the source files, never the generated copies. Sources are `research/`, `synthesis/`, `skills/` and `tools/`. Generated copies are `.agents/skills/` and `.claude/skills/` (from `tools/sync_skills.py`), and `data/`, `skills/*/references/*.json`, `skills/opendesigner/references/stages/` and `chatgpt-project/knowledge/` (from `tools/build_data.py`). Rebuild them and run the local checks below in the same pull request.

## Working with the multi-session protocol

OpenDesigner is built by many parallel sessions (people, Claude, Codex, ChatGPT) that coordinate through plain files in this repo. If you are making a one-off fix, you can skip this and open a normal PR. If you are taking on a research lane or a larger piece of work, follow [`_coordination/PROTOCOL.md`](_coordination/PROTOCOL.md). In short:

```bash
export OD_SESSION="Your name or session name"
python3 tools/od.py status                     # lanes, active sessions, unread messages
python3 tools/od.py claim L19                  # claim a lane before you start
python3 tools/od.py heartbeat "what I am doing"
python3 tools/od.py log "decision and why"     # appends to _coordination/DECISIONS.md
python3 tools/od.py done L19 --summary "12 cards, 80 sources"
```

Maintainers run `python3 tools/od.py sync -m "..."` on their own working copies. External contributors should use a fork and a pull request instead.

To propose a new research lane, add one row to `_coordination/BOARD.md` with status `open` in your PR and describe the scope in the PR body.

## Local checks to run before a pull request

All checks use Python 3.10 or newer and no third-party packages.

```bash
# every JSON file parses
python3 -c "import json,pathlib; [json.loads(p.read_text()) for p in pathlib.Path('.').rglob('*.json') if '.git' not in p.parts]; print('all JSON parses')"

# citation integrity: every cited source id is in a trace, every card id exists
python3 tools/jev_nav.py check

# engine tests (once they are in the repo)
python3 skills/opendesigner/scripts/test_engine.py

# journey tracker tests: the private log, the anonymous report and the consent texts
python3 skills/opendesigner/scripts/test_journey.py

# generated skill copies match skills/, and skill frontmatter stays portable
python3 tools/sync_skills.py --check
python3 tools/build_dist.py --check

# relative links in Markdown files resolve (offline)
python3 tools/check_links.py
```

CI runs the same checks on every pull request (see `.github/workflows/ci.yml`).

## Pull requests

- One topic per PR. Link the issue it closes.
- For research changes, include the trace rows for every new source.
- For skill or engine changes, include a short transcript, a screenshot of the visual, or test output.
- If your change affects a decision other lanes rely on, add a line to "Cross-lane notes" in `_coordination/BOARD.md`.
- Keep commits small. Maintainers squash on merge.
