## F-001 · 2026-10-14 · bug
engine.py review flags pixel-sprite strings in JS (e.g. '...w....w...') as 'three periods in UI text, use the ellipsis' (STD-visual-details-03). They are bitmap rows, not copy; the check should skip script string literals or at least JS arrays.

## F-002 · 2026-10-14 · confusing
engine.py review reports every raw px spacing as breaking STD-accessibility-motion-13 ('write spacing in rem or em') and then suggests var(--ds-space-8), which the generated tokens.css defines in px (--ds-space-8: 8px). Either the space tokens should be rem or the standard's message should accept the px tokens; as written, following the fix still breaks the rule.

## F-003 · 2026-10-14 · gap
Pixel faces need sizes on their own grid (Silkscreen is crisp only at multiples of 8 px: 16, 24, 32). The generated scale (11, 14, 18, 22, 27, 34) has none of them, so the pixel title and kicker sit off the scale on purpose. A displayFace flagged as pixel/bitmap could snap display sizes to its grid.

## F-005 · 2026-10-14 · idea
Warmth only moves the dark neutrals between pure grey (40) and slate blue-grey (0: #191d23); a night indigo shell (#0e1235-like) is not reachable through any dial. Fine for UI, but a 'neutral hue' input (tint the neutrals toward a chosen hue) would let a scene-driven palette like this one carry into the shell.

## F-006 · 2026-10-14 · idea
Style studies: the engine has no notion of a named style (bento, mesh gradient, terminal, pixel art). Each style needed traits the dials cannot carry (tile hierarchy, gradient field, character grid and glyph coverage, pixel grid and integer scaling). A per-style checklist (traits, failure modes, which dials express it) would make these repeatable.
