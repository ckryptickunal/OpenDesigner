# OpenDesigner: extend an existing system

Use this when the project already has an OpenDesigner system (`opendesigner/state.json`, or a DESIGN.md generated by OpenDesigner) and someone wants a change: a new component, a new theme or platform, a tweak to a token, a new brand color, or "why is this blue?". The goal is harmony: new work inherits existing values instead of inventing new ones, and every change is recorded so the next session and the team can follow it.

The engine is `<skills folder>/opendesigner/scripts/engine.py` (the sibling opendesigner skill). Run it from the project root; state lives in `./opendesigner/`.

## 1. Start-up routine (before touching anything)
1. Read, in this order: `opendesigner/DESIGN.md`, `opendesigner/state.json` (answers, dials, hooks, `locks`), `opendesigner/decisions.md` (latest entries last), the token files in `opendesigner/tokens/`, and `git log --oneline -15 -- opendesigner/` if the repo uses git.
2. Run `engine.py validate`. If it fails, report the failures first; fixing them may be the real task.
3. Tell the person in five lines or fewer: the direction, the key values (accent, faces, base size, radius, depth model), the locked decisions, open items (assumed inputs, pending assets), and the validation result.
4. Ask only about what is new. Never re-run the whole interview.

In a chat-only host, ask the person to upload `state.json`, `decisions.md` and the token files (or DESIGN.md at minimum) before changing anything.

## 2. Classify the request
| Request | Treat it as | Do |
|---|---|---|
| "Add a date picker / pricing table / settings page" | New component or pattern | Build it from existing tokens only; list which tokens it uses; add states (hover, focus, disabled, loading, error) and keyboard behavior; add a short entry to DESIGN.md Components |
| "Make buttons a bit rounder", "denser tables" | One decision | Find the question in `<opendesigner>/references/stages/`, show the current value and the options, change it with `pick` or `set`, show what moved downstream |
| "New brand color", "dark mode", "add Android" | A stage re-opened | Re-run that stage's questions only (color stage 08, themes 07, platforms 04), with the same question card as the interview |
| "Make it feel more playful", a new direction | A user challenge | Direction changes touch most decisions. Say what would move (from `graph.json`), propose it as safe choices and risks, and change nothing without explicit confirmation |
| "Why is X like this?" | A question | Answer from `decisions.md` and the Decision Card (`<opendesigner>/references/cards/`); change nothing |
| A value that does not exist yet (a new spacing step, a new color role) | A token addition | Add it through the engine with a reason; never hard-code it in a component |

## 3. Locked decisions and conflicts
- Anything in `state.json` → `locks` (brand hexes, contrast target, reduced-motion policy, and whatever the owner locked) changes only with explicit consent. Name the lock and ask before superseding it.
- If the request conflicts with an earlier decision, show both and let the person choose. Record the choice as a new decision that supersedes the old one; never edit or delete old entries.
- A recommendation you make is not an answer you received: if the person says "you decide", record it as `delegated`.

## 4. Make the change
1. Show the change before committing: the current value, the new value, and the downstream decisions and tokens it moves (`<opendesigner>/references/graph.json` edges from the card id in the stage file). Use a visual template from `<opendesigner>/assets/templates/` when the host can show one.
2. Apply it: `engine.py pick <Q-id> <value> --why "..."` or `engine.py set <path> <value> --why "..."`; `engine.py lock <path>` if the owner wants it locked.
3. Rebuild: `engine.py generate`, then `engine.py validate` (fix errors before showing results), then `engine.py design-md`, and the exports the project uses (`engine.py export --format css` and so on).
4. Show the diff: `git diff --stat opendesigner/` and the changed token values in a short table.

## 5. Drift check (on request, or when asked to "clean up styles")
Scan the codebase for values that bypass the system: `python3 <skills folder>/opendesigner-extract/scripts/css_scan.py src/` lists declared colors, sizes, radii, shadows and durations. Any value not in the tokens is either a missing token (add it) or drift (replace it with the nearest token). Propose the replacements as a list; apply only what the person approves.

## 6. Tell the team
End with a change note a teammate can read in 20 seconds:
```
Design system change, <date>
What changed: <decision, old -> new>
Why: <reason in the owner's words>
Affects: <tokens and components>
Validation: pass | <warnings with waivers>
Decision log: opendesigner/decisions.md, D<n>
```
